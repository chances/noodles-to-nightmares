HUD Timers in GTA III

Mission: make on-screen countdown timers work reliably in GTA III missions and automate wiring them through the FSM compiler and Mission Editor.

1. Why Hud.DisplayTimer(TIMERB) Fails

In 1_shady_job.fsm.json, the DELIVER_DRUGS state had a timeLimit of 180 seconds and manually added Hud.DisplayTimer(TIMERB) to onEnter and Hud.ClearTimer(TIMERB) to onExit. In-game, no HUD timer appeared.

Sanny Builder compiles Hud.DisplayTimer(...) to opcode 014E: set_timer_to %1d%. In the GTA III game engine (class COnscreenTimer / CUserDisplay::OnscnTimer in the RenderWare engine source), opcode 014E operates under two strict constraints:

Engine RequirementWhat TIMERB DoesWhy It Fails
Global ScriptSpace Pointer: 014E reads a byte offset into the global variable buffer (CTheScripts::ScriptSpace). TIMERB is an internal script thread hardware register, not a global variable. Sanny encodes TIMERB as a local variable operand (03 11 00 / local 17). The engine expects global token 02 and an offset, so it reads an invalid address and never registers a clock.
Countdown Value: The variable passed to 014E must hold milliseconds remaining (e.g. 180000). Each frame, the engine automatically subtracts frame delta (CTimer::ms_fTimeStep) and renders MM:SS. TIMERB starts at 0 and counts up continuously. Even if the engine accepted the register, TIMERB starts at zero, meaning a countdown timer would instantly read 00:00.
Opcode 014E strictly requires a global variable (e.g. $hudTimer) initialized to the remaining milliseconds. It cannot take CLEO local variables or TIMERB.

2. Pinned Global Variable: $hudTimer

Because opcode 014E requires a global slot in ScriptSpace, every mission script that displays an on-screen timer must use a shared global variable pinned in variables.txt.

// In variables.txt:
var
  // ...
  $hudTimer: int
end

// Pinned in the Shared section:
Alloc($hudTimer, 4411)

At runtime, displaying the timer requires two operations:

  1. Set the global to total milliseconds: $hudTimer = 180000
  2. Display the countdown: Hud.DisplayTimer($hudTimer) (opcode 014E)

When the timed section finishes or the state exits, opcode 014F: stop_timer $hudTimer (Hud.ClearTimer($hudTimer)) removes the clock from the player's HUD.

3. ❓ Why Shouldn't Authors Write Enter/Exit Steps Manually?

Manually scripting Hud.DisplayTimer and Hud.ClearTimer inside state onEnter and onExit lists introduces three major issues:

  • Leaked Timers on Fail or Abort: If a player fails the mission, gets arrested, or triggers a custom branch before the state's regular exit, missing a ClearTimer call leaves a ghost timer permanently counting down on the screen.
  • Boilerplate & Unit Confusion: Authors must remember to convert seconds to milliseconds, assign $hudTimer, and keep the millisecond limit matched with the state's time limit condition.
  • Redundant Source of Truth: The state already defines timeLimit: 180. Specifying the timer again in step lists violates DRY principles and creates synchronization bugs.

4. The Solution: Compile-Time Inference

Instead of manual steps, the FSM state schema supports a showTimer boolean flag alongside timeLimit. In the Mission Editor Inspector pane, the Time Limit section includes a Show HUD Timer checkbox.

How @noodles/fsm Generates Timed States:
  • On State Entry: The generator emits TIMERB = 0. If showTimer is true, it also emits $hudTimer = {timeLimit * 1000} and Hud.DisplayTimer($hudTimer).
  • In the Tick Loop: The generator watches TIMERB > {timeLimit * 1000} (exceeding it routes to onFail).
  • On State Exit (Leave Routine): The generator calls leaveStateName() on every exit transition (normal completion, branches, and failure). If showTimer is true, leaveStateName() automatically calls Hud.ClearTimer($hudTimer).
